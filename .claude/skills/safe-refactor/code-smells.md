# 壞味道與處理方式

| 壞味道 | 判斷標準 | 處理方式 |
|---|---|---|
| 神秘命名 | 名稱看不出用途（data、tmp、handle2） | 重新命名為表達意圖的名稱 |
| 重複程式碼 | 相同或相似邏輯出現在多處 | 依三次法則判斷後抽取函式 |
| 過長函式 | 一個函式做多件事，無法一眼看完 | 抽取函式，以「做什麼」命名每一段 |
| 過長參數列 | 參數超過 3 個 | 改用參數物件 |
| 全域資料 | 任何地方都能修改的共用狀態 | 封裝為有明確存取介面的模組 |
| 發散式修改 | 一個模組因多種不同原因被修改 | 依變化原因拆分模組 |
| 霰彈式修改 | 一個需求要改多個檔案的小地方 | 將相關邏輯集中到同一處 |
| 依戀情結 | 函式大量使用其他模組的資料 | 將函式搬移到其依賴的模組 |
| 資料泥團 | 同一組資料總是一起出現 | 組成專屬型別或物件 |
| 基本型別偏執 | 用字串或數字表達業務概念（金額、狀態） | 建立專屬型別 |
| 重複條件判斷 | 相同的 switch 或 if (type === ...) 散落多處 | 改用策略模式或對應表 |
| 投機性通用 | 預留但未被使用的抽象、參數、擴充點 | 移除或內聯 |
| 過長訊息鏈 | a.getB().getC().getD() | 提供直接存取的介面 |
| 解釋性註解 | 需要註解才能理解程式在做什麼 | 抽取函式並以註解內容命名；註解只說明「為什麼」 |

## 過度設計（對應 `simple-design.md` 的警訊）
| 壞味道 | 判斷標準 | 處理方式 |
|---|---|---|
| 只為測試存在的方法 | 正式程式碼沒有任何呼叫端 | 刪除，或改從公開介面測試 |
| 錯誤的抽象 | 共用函式為不同呼叫端累積參數與 if | 內聯回各呼叫端，再重新找共通點 |
| 設定驅動的邏輯 | 用設定檔或資料結構模擬流程分支 | 改回直接寫成程式碼 |
| 共用程式碼含業務名詞 | 共用元件的 prop 名稱出現 coupon、member、order 等 | 業務部分移回呼叫端，共用部分只留通用概念 |
