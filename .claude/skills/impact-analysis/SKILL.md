# 影響分析

觸發條件見 `.claude/rules/change-and-release.md` 的「修改既有行為」。

## 步驟
1. **定位目標**：符號名稱、所在模組與層。
2. **找出所有引用**：搜尋符號名稱，也搜尋字串形式（路由、事件名、設定鍵）；介面找出所有實作；DTO 與訊息找出序列化與外部消費端（其他服務、前端、佇列、排程）。
3. **設定鍵另查部署鏈**（範圍見 `change-and-release.md`）。
4. **分類**：直接呼叫端、實作、測試、外部消費者。
5. **判斷變更類型**：新增（相容）、修改語意（危險：簽章不變但行為改變）、修改簽章（breaking）、刪除（breaking）。
6. **輸出表格**：

   | 使用處 | 類型 | 是否需跟著改 | 現有測試 | 風險 |
   |---|---|---|---|---|

7. **建議做法**：依 `change-and-release.md` 的「修改既有行為」；依賴過多時以介面或 adapter 解耦；breaking change 依 `api-and-database.md` 的契約相容表與 `/safe-refactor` 的大型重構策略。
8. 使用者確認後才動手；表格附在 PR 的「影響範圍」。

## 注意
- 沒找到呼叫端也要寫出搜尋方式，不能只說「沒有影響」。
- 修改語意型最容易漏測：逐一確認每個呼叫端對新行為的假設。
- 啟動驗證未涵蓋的設定鍵漏改時不會報錯，只會在執行期以功能失效呈現，必須靠清單攔下。
