# 自動測試

目標不是覆蓋率數字，而是每條業務規則至少有一個測試會在被改壞時失敗。

## 層級
| 層級 | 數量 | 測什麼 | 時機 |
|---|---|---|---|
| 單元 | 多 | 業務規則與純邏輯，不碰 I/O，毫秒級 | 每次 commit |
| 契約快照 | 依需要 | 對外契約（API schema、訊息格式）逐字比對 | 每次 commit |
| 架構 | 少 | 依賴方向、禁用引用（SHOULD 以架構測試工具強制） | 每次 commit |
| 整合 | 適量 | 與資料庫、檔案、外部服務的實際整合 | 標記為整合測試，快速 CI 排除 |
| 端到端 | 少 | 關鍵使用者流程的主要路徑 | 發布前 |

## 涵蓋範圍
- 領域層的公開方法都有單元測試；每個功能的成功路徑與每個錯誤路徑都有測試。
- SHOULD：特性測試（見 `refactoring.md`）以快照鎖定既有行為。
- 覆蓋率是找漏測的工具：不得較主線下降；SHOULD 門檻為領域 90%、應用 80%、整體 70%。MAY 對領域層執行 mutation testing。

## 寫法
- 測行為，不測實作：透過公開介面斷言可觀察的結果；不測私有方法；重構不改行為時測試不應該壞。
- 一個測試只驗證一個行為主題；用 Arrange／Act／Assert，三段以空行分隔。
- 測試名稱描述行為與條件：`方法_情境_預期` 或 `rejects_withdrawal_when_balance_is_insufficient`，全專案擇一。
- 測試內不寫 `if`、迴圈、try/catch；多組資料用參數化測試。
- 用 Builder 或工廠函式建立測試資料並給預設值，測試中只寫出相關欄位。

## 測試替身與獨立性
- 只替換 I/O 邊界：外部 API、寄信、時間、亂數、付款；不 mock 自己的領域物件或被測對象。優先順序：真實物件 > fake > stub > mock。
- 資料庫整合測試用真實資料庫（如容器），不用記憶體模擬的資料庫取代。
- 一個測試需要 mock 超過 3 個依賴，代表受測對象職責太多。
- 測試不依賴執行順序、真實時間、外部網路或共用可變狀態；不用 sleep 等待非同步結果。

## 不穩定測試
- flaky 測試當日修正或隔離；禁以重試掩蓋；隔離超過一週即刪除並開追蹤項目。
