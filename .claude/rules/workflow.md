# 開發流程：極限編程（XP）

## 價值觀
| 價值觀 | 執行規範 |
|---|---|
| 溝通（現場客戶） | 主動揭露資訊；業務規則不明、需求矛盾或有多種合理解讀時，停下提問，不自行假設 |
| 簡單（簡單設計） | 只做目前需要的最簡單解法，判斷依 `simple-design.md` |
| 回饋 | 每個小步驟完成後立即執行測試與檢查，並回報結果 |
| 勇氣 | 驗證失敗、未完成或不確定之處明確回報，未執行的檢查不得回報為通過；方向錯誤時提出重寫評估（範圍、風險、未記錄的邊界情況）由使用者決定，不自行重寫，也不硬補 |
| 尊重 | 遵循專案既有慣例與架構；只改與任務相關的程式碼，不調整無關檔案的格式；範圍外的問題記錄並回報 |

## 實踐
| 實踐 | 執行規範 |
|---|---|
| 小步前進 | 一次只處理一個小任務；超過一個 PR 的範圍（見 `change-and-release.md`）時先提出拆分方案 |
| 計畫先行 | 實作前列出步驟、影響檔案與驗收條件，經確認後再執行 |
| 測試驅動 | 先寫會失敗的測試並執行確認失敗，回報後經確認才開始實作；不可同時產出測試與實作 |
| 驗收測試 | 以使用者行為與需求撰寫測試，不描述實作細節；測試必須能在需求未滿足時失敗 |
| 重構 | 測試通過後檢查重複與命名並整理；其餘依 `refactoring.md` |
| 結對 | 使用者決定方向、AI 執行；設計取捨（包括是否需要抽象）提出選項與利弊，由使用者決定 |
| 持續整合 | 每完成一個循環就 commit；定期同步主線並檢查衝突，需要 merge 或 rebase 時先告知 |
| 集體所有 | 程式碼清楚易讀，不用只有 AI 看得懂的技巧；寫法依 `coding.md` |
| 程式碼規範 | 遵循專案的 lint、formatter 與命名慣例（存檔後由 hook 自動格式化）；提交前執行並修正所有警告 |
| 小版本發布 | 每個 PR 保持可運作、可合併；未完成功能依 `change-and-release.md` 以 feature flag 隔離 |
| 可持續步調 | 不為了快速完成而跳過測試、略過錯誤處理，或修改測試期望值（需求改變並說明者除外） |

## 標準工作循環
計畫 → 紅燈 → 綠燈（剛好通過測試的最少程式碼）→ 重構 → 驗證（完整測試、型別檢查、lint）→ 提交（核對提交前檢查表後 commit 並回報）；紅燈到提交依驗收條件逐一重複。做法見 `/xp-cycle`，修 bug 用 `/fix-bug`。
