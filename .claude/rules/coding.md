# 程式碼規範

錯誤處理、副作用、非同步與日誌見 `reliability.md`。

## 命名
- 名稱讓讀者不開實作即知意圖（`elapsedDays` 而非 `d`）；布林用 `is`／`has`／`can`／`should` 開頭；函式用動詞，類別與變數用名詞。
- 大小寫與前後綴依語言慣例，由 formatter 與 linter 強制。
- 一個概念全專案一個詞（`fetch`／`get`／`retrieve` 擇一）；業務名詞以專案詞彙表為準（若有），新名詞先加入詞彙表再用於程式、測試與文件。
- 名稱長度與作用範圍成正比；不縮寫（`id`、`url` 等通用縮寫除外）；不在名稱中放型別或流水號。
- 名稱需要 `And`、`Or`、`Manager`、`Helper`、`Util` 才說得清楚，代表職責不清，拆分或重新命名。

## 函式與控制流程
- 只做一件事，所有敘述在同一抽象層級，不混合高層編排與低層細節。
- SHOULD：目標 ≤ 20 行；超過 40 行必須拆。
- 參數 ≤ 3 個，更多時改傳參數物件；不用布林旗標參數改變行為。
- 最小驚訝：行為與名稱一致，沒有隱藏副作用（`checkPassword` 不應順便建立 session）。
- 命令查詢分離：改變狀態的函式不回傳查詢結果，查詢函式不改變狀態。
- 用 guard clause 提早返回，主邏輯不被條件包裹，巢狀 ≤ 2 層；複雜條件抽成具名變數或函式；避免否定式條件。

## 排版、註解與重複
- 相關程式碼放在一起；高階函式在上、細節在下；變數在接近使用處宣告。
- 註解只說明「為什麼」（業務背景、非直覺的決定）；需要註解才看得懂時，先改名或抽函式。
- 魔術數字與字串改成具名常數、列舉或值物件。
- DRY：同一條業務知識只寫一處；相似但會因不同原因改變的程式碼保持分開（抽取時機見 `simple-design.md`）。

## 型別
- 有型別系統就開嚴格模式與 null 安全檢查，避免 `any`／`dynamic`；不以強制運算子抑制 null 警告（附註解說明者除外）。
- 用型別讓不合法狀態無法表示；以值物件取代表達業務概念的基本型別。
- 金額用 decimal 或整數最小單位，不用浮點數。

## 其他
- 新增相依套件前確認：標準函式庫做不到、仍在維護、授權可用、無已知漏洞；幾十行能寫完的不引入。
- 不留註解掉的程式碼、未使用的程式碼與除錯輸出；`TODO` 必須附追蹤編號：`TODO(#123)`。
- README 包含用途、啟動與測試方式；跨團隊公開的 API 寫文件註解（用途、參數限制、錯誤情況）。
