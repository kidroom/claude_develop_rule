# 設計原則：避免過度設計

## 核心原則
- **YAGNI**：只實作當前需求明確需要的功能，不為「之後可能會用到」預先撰寫程式或預留設定。
- **KISS**：能用函式解決就不用類別，能用一層解決就不用多層，選擇最容易理解的寫法。
- **最簡可行**：先寫出能通過測試的最簡單版本，複雜度等真正需要時再加入。
- **簡單設計四原則**（依優先順序）：通過所有測試 → 清楚表達意圖 → 沒有重複 → 元素最少。不能改善前三項的類別、介面、層級一律不加。

## 抽象時機
- **三次法則**：第一次直接寫，第二次允許重複，第三次出現同類需求時提出抽象方案，經確認後執行。
- **挨第一顆子彈**：不預測所有變化，某類變化實際發生後，才針對該類變化建立擴充點。
- **重複優於錯誤的抽象**：共用函式開始需要越來越多參數或 if 來應付不同呼叫端時，應拆回各自的實作，再重新找共通點。
- **避免倉促抽象**：共通點尚未明確前，偏好保留重複。
- **延後決策**：重大設計決策延到資訊足夠、再不決定會造成損失時才做。
- 修改共用層前的結構調整見 `refactoring.md` 的預備性重構。

## 系統與架構
- **從簡單演化**：先做出能運作的最小版本，再逐步擴充，不從零設計完整的複雜架構。
- **簡單勝過完整**：不追求涵蓋所有情境，簡單且足夠的設計優於完整但複雜的設計。
- **不過早最佳化**：效能最佳化與通用化都要有實際依據（量測數據或明確需求）才進行。
- **聚焦實際問題**：不建立通用框架或平台，除非當前需求確實需要。

## 過度設計警訊（出現時應考慮簡化）
- 只有一個實作的介面或抽象類別
- 從未被傳入不同值的參數或設定選項
- 只被測試呼叫的方法
- 為了「彈性」新增、但目前沒有任何呼叫端使用的擴充點
- 用設定檔或資料結構模擬原本用程式碼寫更清楚的邏輯
- 共用元件的 prop 名稱出現業務名詞（如 coupon、member、order）

簡化手法見 `/safe-refactor` 的壞味道對照表。

## 平衡原則
- 以上原則用於避免「過度」設計，不是反對設計。
- 已確定會持續增加的變化方向（如付款方式、通知管道、API 攔截器），應依開放封閉原則預留擴充點，不可用 YAGNI 為由持續堆疊 if-else。
- 判斷依據是「真實發生的變化」，而不是「想像中的變化」；不確定時依 `workflow.md` 的結對原則提出選項。
