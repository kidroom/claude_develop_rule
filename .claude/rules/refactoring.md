# 重構原則

> 重構＝不改變外部行為的前提下改善內部結構，不是重寫、修 bug 或加功能。
> 執行步驟、壞味道對照與大型重構策略見 `/safe-refactor`；抽象時機（三次法則）見 `simple-design.md`。

## 重構時機
| 法則 | 執行規範 |
|---|---|
| 預備性重構 | 先讓改變變容易，再做容易的改變：新功能難以加入或要修改共用層時，先以獨立 PR 調整結構（行為不變），再於後續 PR 實作 |
| 理解性重構 | 遇到難懂的命名或邏輯，以重新命名或抽取函式把理解寫回程式碼 |
| 童子軍法則 | 讓程式碼比來時更乾淨，但僅限當前修改範圍附近 |
| 機會性優先／範圍控制 | 重構服務於當前任務；只重構任務相關的程式碼，不重新設計整個模組；無關的重構需求記錄並回報，不自行處理 |

## 執行方式
| 法則 | 執行規範 |
|---|---|
| 測試先行／特性測試 | 重構前確認有測試覆蓋；沒有就先寫特性測試記錄現有行為，包含看似不合理的行為，不順手修正 |
| 兩頂帽子 | 同一時間只做功能或只做重構；分開 commit，message 標明 `refactor:` 或 `feat:` |
| 行為不變 | 不可修改任何測試的預期結果；需要修改才能通過時，代表行為改變，應停止並回報 |
| 小步前進／保持綠燈／頻繁提交 | 每次只執行一種重構手法，通過測試即 commit；失敗且無法立即修正時退回上一個通過狀態，以更小步驟重來 |

## 禁止或暫緩重構的情境
| 情境 | 執行規範 |
|---|---|
| 程式碼穩定且無修改需求 | 不重構，除非當前任務需要修改它 |
| 無測試且無法補測試 | 僅執行工具層級的安全重構（如重新命名），其他結構調整回報後暫緩 |
| 接近發布時間點 | 不進行非必要的結構調整 |
| 僅出於寫法偏好 | 不重構；重構必須有明確目的（便於後續修改、提升可讀性、消除實際問題） |
| 考慮重寫而非重構 | 依 `workflow.md` 的勇氣原則提出評估，由使用者決定 |
