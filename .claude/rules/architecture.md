# 架構與目錄結構

## 分層
```
介面層（handler / controller / UI / CLI）：解析輸入 → 呼叫用例 → 轉換輸出；不含業務規則
  ▼
應用／領域層（use case / domain）：業務規則；盡量是純邏輯
  ▼  透過領域層定義的介面或函式參數
基礎設施層：資料庫、外部 API、檔案、時間
```
- 依賴只能由上往下；領域層不 import 框架、資料庫、HTTP 函式庫。
- 物件組裝（依賴注入）集中在程式進入點；相依注入生命週期明確，長生命週期（singleton）物件必須無狀態或執行緒安全。
- 載入或匯入模組時不得產生副作用（建立連線、讀取設定）；初始化放在進入點。
- 橫切關注點（日誌、重試、逾時、追蹤）以 middleware、decorator 或框架掛鉤實作，不寫進業務邏輯。
- 資料轉換集中在明確的 mapper 或用例，不散落在各處。
- 依規模選層數，痛點實際出現（同一規則在兩處重複、測規則必須啟動資料庫）才升級：腳本或一次性工具用單一模組；CRUD 為主用介面層＋資料存取，不硬加 service；有實質業務規則才三層完整拆分。
- 禁止：沒有實際需求的微服務、事件匯流排、CQRS；通用 `BaseRepository<T>`、`BaseService`；跨層捷徑（介面層直接操作資料庫）。

## 邊界
- 外部輸入在介面層驗證並轉成領域型別，進入內部後信任型別，不重複檢查（驗證要求見 `security.md`）。
- 設定與環境變數集中一處讀取，以具型別的設定物件提供預設值並在啟動時驗證，缺必要設定即啟動失敗。
- 每層只暴露最小契約。

## 目錄結構
語言或框架有強烈慣例時以其為準；其餘依功能分包，改一個功能只動一個目錄。
```
src/
  orders/      # 功能目錄，用業務名詞命名：order.*、order-service.*、order-repository.*、order-handler.*、order.test.*
  shared/      # 兩個以上功能「已經」共用才放
  config.*     # 集中讀取設定
  main.*       # 組裝依賴、啟動
tests/         # integration/、e2e/
```
- 不依技術層分頂層目錄（`controllers/`、`services/` 各放全部功能），除非框架強制；新開頂層目錄前先詢問。
- 禁止 `utils/`、`helpers/`、`common/`、`misc/`；共用程式碼依主題命名（`shared/money.*`），只剩一個使用方時搬回該功能目錄。
- 巢狀深度 ≤ 4 層；不預先建立空目錄；一個目錄超過約 10 個檔案再拆子目錄。
- 一檔一個主要概念，檔名與其主要類別或函式一致；新增檔案沿用該目錄既有的命名與寫法。
- 單元測試與原始碼同目錄（或依語言慣例鏡像）；整合與 e2e 測試放 `tests/`。
- 功能之間不引用彼此的內部檔案；出現循環依賴代表邊界劃錯，需重新切分。
